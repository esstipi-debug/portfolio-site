Case Study — AI & Decisions

What should an AI be allowed to decide in inventory planning?

Not the numbers. A language model is good at reading a plain-language request and bad at being accountable for a reorder quantity. In the system I built, the model does three narrow things — breaks a tie when a request is ambiguous, reads a document into a fixed schema, and rewrites one summary sentence. Every number in every deliverable comes from deterministic code and passes a QA gate before anything ships. Take the model away and the whole pipeline still runs.

How a request moves

A request is matched against a registry of 50 tools by keyword first. The model is consulted only when that match is ambiguous, and its answer is discarded unless it names a tool that actually exists.

The chosen tool runs through the same prepare → run → QA → deliver pipeline as every other one. If QA fails, nothing is delivered. That check lives in one place, not inside each tool.

Citations come from a 3,019-node knowledge graph built from the supply chain literature. A citation that does not hold up against the graph is vetoed rather than shown.

Two guarantees

Never a dead end. Every consequential result ends one of four ways: executed, ranked options, a prepared handoff such as a pre-filled purchase order or count sheet, or an escalation. Nothing written without approval. A change to a system of record — an Odoo ERP, a Shopify store — is staged as a dry-run changeset, classified by risk, and held for time-boxed human approval, with idempotent apply and rollback. Those write paths are built and tested against in-memory stand-ins. The deployed version is read-only by design, and none of them has been run against a client’s live system.

What it is not

It is not an autonomous agent that picks and chains tools on its own. That is a choice, not a gap: a system that cannot say which tool produced a number should not be allowed to produce it.

And it has no external user yet. It is deployed and I can walk you through it; it has not run a client’s operation.

How the models behind it compare

Each model behind the tools is checked against the shortcut most teams use instead.

~19%More accurate than naive persistence on M5 held-out data
29%Cheaper per year than ordering in round lots
79%The real service level of the “20% of demand” rule, against a 95% target
6.7%Less holding cost from placing buffers across a chain instead of at one node

Each number has its own page: forecasting, safety stock and EOQ, and the network.
